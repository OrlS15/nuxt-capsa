The `driver` key picks the Drizzle driver a database connects with, among the ones its `dialect` accepts. Install the driver's package, when it has one, next to `drizzle-orm`. The driver reads its connection from the database's variable, such as `NUXT_CAPSA_DB_DEFAULT_CONNECTION`.

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-capsa'],
  capsa: {
    db: {
      default: { provider: 'drizzle', dialect: 'postgresql', driver: 'node-postgres' },
    },
  },
})
```

A driver's local default is the database it opens when that variable is unset. [Connection](/database/drizzle/connection) covers both in depth.

## Local databases

Drivers with a local default keep the database in a folder or file under `.data/capsa/db`, which the `dataDir` key moves ([Local default](/database/drizzle/connection#local-default)).

::warning
PGlite opens a store from one process at a time. Stop the server before running `drizzle-kit push`, `migrate` or `studio` on the same store. Otherwise drizzle-kit reports success, the running server never sees the change, and the change is gone after a restart.
::

## Bun drivers

`bun-sql/postgres`, `bun-sql/mysql`, `bun-sqlite` and `bun-sql/sqlite` use clients built into Bun, so both `nuxt dev` and the built server must run on Bun.

```bash [Terminal]
bun --bun run dev
bun .output/server/index.mjs
```

With `bun-sql/sqlite`, start the path with `file:`, since Bun and drizzle-kit both open that form.

## HTTP drivers

`neon-http`, `netlify-db`, `planetscale-serverless` and `tidb-serverless` send each query as an HTTP request. They keep no connection open, so there is nothing to close when the server stops.

```bash [.env]
NUXT_CAPSA_DB_DEFAULT_CONNECTION=postgresql://user:password@ep-example-123456.eu-central-1.aws.neon.tech/neondb?sslmode=require
```

With [migrations](/database/drizzle/migrations) on, `neon-http` applies them over a separate `neon-serverless` WebSocket connection, opened only for that run. A `client` from `config.ts` isn't used for it.

## Turso auth token

A remote libSQL database, such as one on Turso, also needs its auth token. The `libsql` drivers read it from the URL, both in the server and in drizzle-kit, so the token goes into the same variable as the address.

```bash [.env]
NUXT_CAPSA_DB_DEFAULT_CONNECTION=libsql://my-db-my-org.turso.io?authToken=…
```

## Cloudflare D1

A Worker reaches D1 through a binding, so the connection is the binding's name, and replicas are further binding names. D1 needs Nitro's Cloudflare preset and wrangler, also in `nuxt dev`.

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  capsa: {
    db: {
      default: { provider: 'drizzle', dialect: 'sqlite', driver: 'd1' },
    },
  },
  nitro: { preset: 'cloudflare-module' },
})
```

::code-group

```jsonc [wrangler.jsonc]
{
  "d1_databases": [
    { "binding": "DB", "database_name": "app", "database_id": "<database id>" }
  ]
}
```

```bash [.env]
NUXT_CAPSA_DB_DEFAULT_CONNECTION=DB
```

::

drizzle-kit can't use a binding: it reaches D1 over Cloudflare's HTTP API (`d1-http`), with the credentials returned from the `kit` hook. drizzle-kit loads `config.ts` too, so never read the binding there.

```ts twoslash [server/capsa/db/default/config.ts]
import { defineDbConfig } from 'nuxt-capsa/db'

export default defineDbConfig('default', {
  kit: () => ({
    dbCredentials: {
      accountId: process.env.CLOUDFLARE_ACCOUNT_ID!,
      databaseId: process.env.CLOUDFLARE_DATABASE_ID!,
      token: process.env.CLOUDFLARE_D1_TOKEN!,
    },
  }),
})
```

Drizzle explains where to find these values: [D1 HTTP with drizzle-kit](https://orm.drizzle.team/docs/guides/d1-http-with-drizzle-kit).

## AWS Data API

`aws-data-api/pg` takes its connection as a JSON object with the database and the ARNs of the cluster and its secret. AWS credentials come from the standard AWS variables and can't go in that object.

```bash [.env]
NUXT_CAPSA_DB_DEFAULT_CONNECTION='{"database":"app","resourceArn":"arn:aws:rds:eu-west-1:123456789012:cluster:app","secretArn":"arn:aws:secretsmanager:eu-west-1:123456789012:secret:app"}'
AWS_REGION=eu-west-1
AWS_ACCESS_KEY_ID=…
AWS_SECRET_ACCESS_KEY=…
```

drizzle-kit receives the same object as its `dbCredentials`, and `options` in `config.ts` receives it as `connection`.

## Your own client

To connect through a client you build, such as a pool, return it as `client` from `options` in the database's `config.ts` ([A client of your own](/database/drizzle/config-file#a-client-of-your-own)).

```ts [server/capsa/db/default/config.ts]
import mysql from 'mysql2'
import { defineDbConfig } from 'nuxt-capsa/db'

export default defineDbConfig('default', {
  options: ({ connection }) => ({ client: mysql.createPool(connection) }),
})
```

## CockroachDB settings

The connection must turn off `autocommit_before_ddl`, through the `options` parameter of the URL. On CockroachDB 26.3, also turn off `create_table_with_schema_locked`, or the second migration fails with "table is locked".

```bash [.env]
NUXT_CAPSA_DB_DEFAULT_CONNECTION="postgresql://root@localhost:26257/app?options=-c autocommit_before_ddl=off -c create_table_with_schema_locked=false"
```

## SQL Server connection

`node-mssql` takes a URL such as `mssql://sa:secret@localhost:1433/app`. When the password contains `@` or `%`, write the connection in the ADO form.

```bash [.env]
NUXT_CAPSA_DB_DEFAULT_CONNECTION="Server=localhost,1433;Database=app;User Id=sa;Password=p@ss%word"
```
