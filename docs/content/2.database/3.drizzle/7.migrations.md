---
title: Migrations
description: Generate migrations with drizzle-kit and let the server apply them, on start or when your code asks.
---

drizzle-kit writes the migrations and the server applies them. The `migrations` option of each database decides when.

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  capsa: {
    db: {
      default: { provider: 'drizzle', dialect: 'postgresql', driver: 'pglite', migrations: 'onStart' },
      analytics: { provider: 'drizzle', dialect: 'sqlite', driver: 'node-sqlite', migrations: 'manual' },
    },
  },
})
```

| Value | Shipped with the server | Migrations run |
|---|---|---|
| `false` (default) | nothing | when you run `drizzle-kit migrate` or `drizzle-kit push` |
| `'manual'` | every `migration.sql`, plus `applyMigrations()` and `ensureMigrations()` | when your code calls those functions |
| `'onStart'` | the same as `'manual'` | as the server starts, before it answers a request |

## From schema to database

::steps
### Change the schema

Add or edit tables in the database's [schema files](/database/drizzle/schema).

### Generate a migration

drizzle-kit compares the schema with the last migration and writes a new folder into `server/capsa/db/default/migrations/`.

```bash [Terminal]
npx drizzle-kit generate --config .nuxt/capsa/db/default/drizzle.config.ts
```

### Start the server

With `'onStart'` the next start applies it. A running `nuxt dev` reloads when the new folder appears and applies it then.
::

[Config file](/database/drizzle/config-file) covers the generated drizzle-kit config and the package.json scripts that shorten these commands.

## Migration files

Each database keeps its migrations in the project's `server/capsa/db/<name>/migrations/`, one folder per migration, applied in folder-name order. Every `migration.sql` travels inside the server bundle (the snapshots stay behind), so a deployed server needs no migrations folder.

```bash [Project]
server/capsa/db/default/migrations/
├── 20261005080406_fast_nicolaos/
│   ├── migration.sql
│   └── snapshot.json
└── 20261005080457_add_body/
    ├── migration.sql
    └── snapshot.json
```

A database without the folder has nothing to apply. A layer's `migrations/` folder is never shipped: [Layers](/database/drizzle/layers) explains how layer tables reach the project's migrations.

::warning
Leave drizzle-kit's `out` alone in the `kit` hook. If you move it, drizzle-kit writes new migrations where the server never looks, and the build leaves them out without an error.
::

## Apply on start

With `'onStart'` the migrations begin as the server boots, and every HTTP request waits until they are applied. Nitro plugins and tasks aren't held back, so they should await `ensureMigrations()` before using the database.

```ts twoslash [server/plugins/posts.ts]
import { definePlugin } from 'nitro'
import { ensureMigrations } from '#capsa/db/default'

export default definePlugin(async () => {
  await ensureMigrations()
  const posts = await useCapsaDb().query.posts.findMany({ columns: { id: true, title: true } })
  console.log(`${posts.length} posts`)
})
```

A failing migration doesn't stop the boot. The server retries it at the first request, then logs both errors and exits with code 1:

```text [Terminal]
[capsa] db source "default": could not apply migrations, stopping the server
On start: DrizzleQueryError: Failed query:
INSERT INTO "nope" ("title") VALUES ('x');
…
At the first request: DrizzleQueryError: Failed query:
INSERT INTO "nope" ("title") VALUES ('x');
…
```

Prerendering skips the migrations, so `nuxt generate` and prerendered routes never migrate the build machine's database.

## Apply from your code

With `'manual'` or `'onStart'`, `#capsa/db/<name>` exports `ensureMigrations()` and `applyMigrations()`. `ensureMigrations()` starts a run only when none is under way or has succeeded. Parallel calls share one run, and the next call after a failure tries again.

```ts twoslash [server/api/track.post.ts]
import { defineEventHandler } from 'nuxt/server'
import { ensureMigrations, getDb } from '#capsa/db/analytics'
import { events } from '#capsa/db/analytics/schema'

export default defineEventHandler(async () => {
  await ensureMigrations()
  const [event] = await getDb().insert(events).values({ name: 'view', at: new Date() }).returning()
  //     ^?
  return event
})
```

`applyMigrations()` starts a new run on every call, for example from a [Nitro task](https://nitro.build/docs/tasks).

```ts twoslash [server/tasks/db/migrate.ts]
import { defineTask } from 'nitro/task'
import { applyMigrations } from '#capsa/db/analytics'

export default defineTask({
  meta: { description: 'Apply the pending analytics migrations' },
  async run() {
    await applyMigrations()
    return { result: 'ok' }
  },
})
```

## drizzle-kit migrate

The server and [`drizzle-kit migrate`](https://orm.drizzle.team/docs/drizzle-kit-migrate) record migrations by folder name in the same table, so whatever one has applied, the other skips.

```bash [Terminal]
npx drizzle-kit migrate --config .nuxt/capsa/db/default/drizzle.config.ts
```

## Migrations table

Applied migrations go into Drizzle's default table: `drizzle.__drizzle_migrations` on postgresql, `__drizzle_migrations` on sqlite. Set another one in the `kit` hook of the database's `config.ts`, which the server reads too.

```ts twoslash [server/capsa/db/default/config.ts]
import { defineDbConfig } from 'nuxt-capsa/db'

export default defineDbConfig('default', {
  kit: () => ({ migrations: { table: 'history', schema: 'drizzle' } }),
})
```

## Several instances

What keeps instances that start together from applying a migration twice depends on the dialect.

| Dialect | Instances starting together |
|---|---|
| postgresql, mysql, mssql | A lock per database: one instance migrates while the others wait. |
| sqlite with libsql or d1 | Each run is one atomic batch. |
| cockroach, singlestore | No lock: one instance may fail, and a restart finds everything applied. |

On postgresql and sqlite a failed run applies nothing. MySQL and SingleStore commit DDL as it runs, so a failed run can leave tables behind.

## Seed data

Seed rows go in a [custom migration](https://orm.drizzle.team/docs/kit-custom-migrations): drizzle-kit creates an empty `migration.sql` for you to fill.

```bash [Terminal]
npx drizzle-kit generate --custom --name=seed --config .nuxt/capsa/db/default/drizzle.config.ts
```

Separate statements with `--> statement-breakpoint`, as drizzle-kit does: pglite, for one, rejects several statements without them.

```sql [server/capsa/db/default/migrations/20261005081259_seed/migration.sql]
INSERT INTO "users" ("name", "email") VALUES ('Ada', 'ada@example.com');
--> statement-breakpoint
INSERT INTO "posts" ("authorId", "title") VALUES (1, 'Hello');
```

## Serverless and Workers

On Cloudflare Workers the start attempt can't reach the database, so the first request applies the migrations, and while a migration fails every request retries it and answers 500. On serverless hosts, prefer `'manual'` or `drizzle-kit migrate` in the deploy step.

## Build errors

With `migrations` on, the build stops on a folder in drizzle-kit's old format and on a migration folder name that Nitro's storage can't read back.

```text [Terminal]
ERROR  [capsa] db source "default": /app/server/capsa/db/default/migrations holds migrations in the old drizzle-kit format. Run drizzle-kit up.
ERROR  [capsa] db source "default": rename the migration folder "20261005090000_what?", Nitro's storage cannot read back a name with "?", ":" or "\".
```

[`drizzle-kit up`](https://orm.drizzle.team/docs/drizzle-kit-up) converts the old format.
