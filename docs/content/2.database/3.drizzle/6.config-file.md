---
title: Config File
description: Pass extra options to drizzle() and drizzle-kit for one database, and run drizzle-kit with the config Capsa writes for it.
---

A database can have a `config.ts` in its folder. It changes what Capsa passes to `drizzle()` when the server opens the database, and what it hands to drizzle-kit.

```ts twoslash [server/capsa/db/default/config.ts]
import { defineDbConfig } from 'nuxt-capsa/db'

export default defineDbConfig('default', {
  options: () => ({ logger: true }),
  kit: () => ({ migrations: { table: 'history' } }),
})
```

## Where it goes

The file is optional and sits next to the database's schema. Only the project's file counts: a layer's `config.ts` is [ignored with a warning](/database/drizzle/layers#project-only-files).

```bash [Project]
server/capsa/db/
├── default/
│   ├── config.ts
│   ├── relations.ts
│   └── schema/
└── analytics/
    ├── config.ts
    └── schema.ts
```

## Name the database

The first argument of `defineDbConfig` names the database the file belongs to, so each hook gets that database's connection and its driver's options. A name that isn't configured:

```ts twoslash [server/capsa/db/analytics/config.ts]
// @errors: 2345
import { defineDbConfig } from 'nuxt-capsa/db'

export default defineDbConfig('analytic', {
  options: () => ({ logger: true }),
})
```

## Hooks

::field-group
  :::field{name="options" type="function"}
  Receives `{ connection, relations }` and returns options for this driver's `drizzle()` call, such as `logger`, `cache`, a changed `connection` or a `client` of your own. It runs once, when the server first uses the database.
  :::

  :::field{name="kit" type="function"}
  Receives the drizzle-kit config Capsa built and returns changes to it. drizzle-kit uses the whole result. The server reads `migrations.table` and `migrations.schema` from it, so both apply migrations through the same table. It is only available when drizzle-kit is installed.
  :::
::

Each hook returns only what it changes, and Capsa merges that over its own values. Yours win, nested objects merge, arrays are joined with your items first, and `undefined` keeps Capsa's value. The options themselves are Drizzle's: [logging](https://orm.drizzle.team/docs/goodies#logging), [cache](https://orm.drizzle.team/docs/cache), [drizzle-kit config](https://orm.drizzle.team/docs/drizzle-config-file).

::warning
Choose the migrations table before any migration is applied. Under a new table name, the server and drizzle-kit find no applied migrations and run them all again.
::

## A client of your own

A `client` replaces the connection Capsa would open, for example to load a PGlite extension:

```ts twoslash [server/capsa/db/default/config.ts]
import { PGlite } from '@electric-sql/pglite'
import { citext } from '@electric-sql/pglite/contrib/citext'
import { defineDbConfig } from 'nuxt-capsa/db'

export default defineDbConfig('default', {
  options: ({ connection }) => ({ client: new PGlite(connection, { extensions: { citext } }) }),
  //          ^?
})
```

With your own client, the connection variable is no longer required and Capsa never closes the client. Replicas are refused with ``replicas can't be used with a `client` from config.ts. Remove NUXT_CAPSA_DB_DEFAULT_REPLICAS or the client.`` [Drivers](/database/drizzle/drivers#your-own-client) shows a pool for another driver.

## No Nitro auto-imports

drizzle-kit loads `config.ts` too, outside Nitro, so import everything the file uses.

## The drizzle-kit config

When drizzle-kit is installed, `nuxt prepare` and `nuxt dev` write one drizzle-kit config per database, and `nuxt dev` rewrites it when files are added to or removed from the database's folder. It reads the schema of the project and every layer, writes migrations into the project's `migrations/` folder, takes the connection from the same environment variable as the server, and applies your `kit` hook last.

```ts [.nuxt/capsa/db/default/drizzle.config.ts]
import config from '<root>/server/capsa/db/default/config'

const capsa = {
  dialect: "postgresql",
  driver: "pglite",
  schema: ["<root>/server/capsa/db/default/schema.ts", "<root>/server/capsa/db/default/schema/**/*.ts", "<root>/layers/shop/server/capsa/db/default/schema.ts", "<root>/layers/shop/server/capsa/db/default/schema/**/*.ts"],
  out: "<root>/server/capsa/db/default/migrations",
  dbCredentials: { url: process.env.NUXT_CAPSA_DB_DEFAULT_CONNECTION ?? ".data/capsa/db/default" },
}

export default config.kit?.(capsa) ?? capsa
```

[Connection](/database/drizzle/connection) explains where the connection and the local default come from.

## Run drizzle-kit

Pass the file with `--config`, from the project root. drizzle-kit reads `.env` and resolves the local database from the folder it runs in, so anywhere else it opens a different database.

```json [package.json]
{
  "scripts": {
    "postinstall": "nuxt prepare",
    "db:generate": "drizzle-kit generate --config .nuxt/capsa/db/default/drizzle.config.ts",
    "db:migrate": "drizzle-kit migrate --config .nuxt/capsa/db/default/drizzle.config.ts",
    "db:studio": "drizzle-kit studio --config .nuxt/capsa/db/default/drizzle.config.ts"
  }
}
```

Each database has its own file, such as `.nuxt/capsa/db/analytics/drizzle.config.ts`. The commands are documented in [drizzle-kit](https://orm.drizzle.team/docs/kit-overview), and [Migrations](/database/drizzle/migrations) covers what the server does with the files they generate.

::warning
With [another driver in development](/database/drizzle/setup#another-driver-per-environment), the file follows the command that wrote it last: `nuxt prepare` writes the production driver, `nuxt dev` the development one. Run `nuxt dev` once before `drizzle-kit migrate`, `push` or `studio`, or they connect with the production driver instead of opening the local database. `drizzle-kit generate` connects to nothing, so it works either way.
::
