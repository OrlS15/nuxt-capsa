Capsa reads each database's connection from an environment variable when the server runs, so connection strings stay out of `nuxt.config.ts`. The variable is `NUXT_CAPSA_DB_<NAME>_CONNECTION`, with the database name in upper snake case.

```bash [.env]
NUXT_CAPSA_DB_DEFAULT_CONNECTION=postgres://app:secret@localhost:5432/app
NUXT_CAPSA_DB_ANALYTICS_CONNECTION=/srv/data/analytics.db
```

[Multiple databases](/database/multiple-databases#connection-variables) covers how camelCase names are spelled.

## Development and production

`nuxt dev` loads `.env` from the project root. A built server reads only its real environment, so set the variables where it runs.

```bash [Terminal]
NUXT_CAPSA_DB_DEFAULT_CONNECTION=postgres://app:secret@db.internal:5432/app node .output/server/index.mjs
```

## In `nuxt.config.ts`

A value in `runtimeConfig.capsa.db.<name>` replaces Capsa's default, and the environment variable still overrides it. The value is written into the build, so keep secrets in the environment.

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  runtimeConfig: {
    capsa: { db: { default: { connection: 'postgres://localhost:5432/app' } } },
  },
})
```

## Local default

Drivers that keep the database in a local file or folder work without the variable. When it is not set, the database lives under `dataDir`, which defaults to `.data/capsa/db`.

| Driver | Store when the variable is not set |
| --- | --- |
| `pglite` | `.data/capsa/db/<name>` (a folder) |
| `libsql`, `libsql/node`, `libsql/sqlite3`, `libsql/wasm`, `bun-sql/sqlite` | `file:.data/capsa/db/<name>.db` |
| `better-sqlite3`, `node-sqlite`, `bun-sqlite`, `tursodatabase/database`, `tursodatabase/wasm`, `tursodatabase-sync` | `.data/capsa/db/<name>.db` |

`dataDir` moves that folder, and Capsa creates it the first time it's needed.

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  capsa: {
    db: {
      // stored in .db/default
      default: { provider: 'drizzle', dialect: 'postgresql', driver: 'pglite', dataDir: '.db' },
    },
  },
})
```

`nuxt dev` resolves the folder from the project root. A built server resolves it from the directory it starts in, as Nitro does with its own `.data`. The [generated drizzle-kit config](/database/drizzle/config-file) reads the same variable and falls back to the same default.

::note
The default only applies while the variable is unset. An empty value still counts as set, so you get the missing-connection error shown under [Remote drivers](#remote-drivers).
::

## Memory and custom paths

The variable accepts any value the driver does, in-memory databases included.

```bash [.env]
NUXT_CAPSA_DB_DEFAULT_CONNECTION=memory://
NUXT_CAPSA_DB_ANALYTICS_CONNECTION=:memory:
```

For a path of your own, make sure its parent folder exists, because Capsa only creates the folder for its default.

## Remote drivers

A driver that connects to a server has no local default, so it needs the variable. If it's missing, `useCapsaDb()` throws:

```text [Terminal]
[capsa] db source "default" has no connection. Set NUXT_CAPSA_DB_DEFAULT_CONNECTION, or return a `client` from `options` in its config.ts.
```

Since nothing is stored locally, these drivers don't take `dataDir`:

```ts twoslash [nuxt.config.ts]
// @errors: 2353
export default defineNuxtConfig({
  capsa: {
    db: {
      default: { provider: 'drizzle', dialect: 'postgresql', driver: 'node-postgres', dataDir: '.db' },
    },
  },
})
```

[Drivers](/database/drizzle/drivers) lists the value each driver expects.

## Read replicas

`NUXT_CAPSA_DB_<NAME>_REPLICAS` takes a JSON array of connection strings.

```bash [.env]
NUXT_CAPSA_DB_DEFAULT_CONNECTION=postgres://primary.internal:5432/app
NUXT_CAPSA_DB_DEFAULT_REPLICAS='["postgres://replica-1.internal:5432/app","postgres://replica-2.internal:5432/app"]'
```

Every query still goes to the primary, and a query sent through `db.$replica` goes to one of the replicas instead, the way Drizzle's [`withReplicas`](https://orm.drizzle.team/docs/read-replicas) works. Migrations always run on the primary. `db.$replica` is `undefined` when no replicas are set, so a read that may lag behind the latest write uses `db.$replica ?? db`.

```ts twoslash [server/api/posts/index.get.ts]
import { defineEventHandler } from 'nuxt/server'

export default defineEventHandler(async () => {
  const db = useCapsaDb()
  const posts = await (db.$replica ?? db).query.posts.findMany({ orderBy: { id: 'desc' }, limit: 20 })
  //    ^?
  return posts
})
```

You can't combine replicas with a `client` of your own from [`config.ts`](/database/drizzle/config-file#a-client-of-your-own).

## Opening and closing

A database connects the first time `useCapsaDb()` or `getDb()` is called in the server process, and later calls reuse that connection. With `migrations: 'onStart'`, the first call happens when the server starts (see [Migrations](/database/drizzle/migrations)).

Capsa closes the connections it opened, replicas included, when the server stops and whenever `nuxt dev` reloads it. A `client` you return from [`config.ts`](/database/drizzle/config-file#a-client-of-your-own) is yours to manage, and Capsa never closes it.

## Serverless and edge

Every serverless instance or Worker isolate opens its own connection on first use. An embedded store lasts only as long as that instance's disk, so point these hosts at a remote database. Cloudflare D1 takes a binding name as its connection (see [Drivers](/database/drizzle/drivers)), and [Migrations](/database/drizzle/migrations) explains how `'onStart'` behaves on these hosts.
